# 06 — เจอปัญหาแล้วแจ้งใคร และอะไรควรบล็อกการ merge

> workflow: [`.github/workflows/security-issues.yml`](../.github/workflows/security-issues.yml) · สคริปต์ตั้งค่า: [`scripts/setup-repo-protection.sh`](../scripts/setup-repo-protection.sh)

pipeline ที่ตรวจเก่งแค่ไหนก็ไร้ประโยชน์ ถ้าผลการตรวจไปจบอยู่ในที่ที่ไม่มีใครเปิด
บทนี้ว่าด้วยเรื่อง "แล้วยังไงต่อ"

## ช่องทางแจ้งเตือนที่ GitHub รองรับ และควรใช้อันไหนเมื่อไหร่

| ช่องทาง                                 | เห็นตอนไหน                   | เหมาะกับ                        | ข้อเสีย                              |
| --------------------------------------- | ---------------------------- | ------------------------------- | ------------------------------------ |
| **ผลของ check ในหน้า PR**               | ทันทีที่ CI เสร็จ            | บอกว่าผ่าน/ไม่ผ่าน              | ไม่บอกว่าผิดตรงไหนถ้าไม่กดเข้าไป     |
| **Job Summary**                         | เปิด workflow run            | ตารางสรุปละเอียด                | ต้องกดออกจาก PR ไปดู                 |
| **คอมเมนต์ใน PR**                       | ทันทีในหน้าที่กำลังรีวิวอยู่ | สรุปสั้นให้คนรีวิวเห็น          | ถ้าทำไม่ดีจะกลายเป็นคอมเมนต์สแปม     |
| **Annotation บนบรรทัดโค้ด**             | ในแท็บ Files changed         | ปักหมุดตรงจุดที่ผิด             | จำกัดจำนวนต่อ run                    |
| **แท็บ Security (code scanning alert)** | ตลอดเวลา                     | ติดตามสถานะ เปิด/แก้แล้ว/ยกเว้น | ไม่มีใครเปิดถ้าไม่มีใครสั่งให้เปิด   |
| **Issue**                               | ในคิวงานปกติของทีม           | ของที่ต้องมีเจ้าของและกำหนดเวลา | ถ้าสร้างอัตโนมัติมากไปจะกลายเป็นขยะ  |
| **อีเมล / Slack / LINE**                | ทันที                        | เรื่องด่วนที่ต้องรู้ตอนนี้      | ถ้าส่งทุกเรื่องจะถูกปิดแจ้งเตือนทิ้ง |

repo นี้ใช้ 6 ช่องทางแรกครบ ส่วนช่องทางสุดท้ายต่อเพิ่มได้ด้วย action อย่าง `slackapi/slack-github-action`

## หลักการเลือกช่องทาง

จัดตามคำถามว่า **"คนรับต้องทำอะไรกับข้อมูลนี้ และต้องทำเมื่อไหร่"**

- ต้องแก้ก่อน merge → ต้องอยู่ใน PR (check + คอมเมนต์)
- ต้องแก้แต่ไม่ด่วน → Issue ที่มีเจ้าของ
- ไว้ดูย้อนหลัง/ตรวจสอบ → แท็บ Security + artifact
- ต้องรู้ทันทีตอนตีสาม → แจ้งเข้าแชต (แต่ต้องกลั่นกรองมาก ๆ)

## คอมเมนต์ใน PR แบบไม่สแปม: sticky comment

ถ้าคอมเมนต์ใหม่ทุกครั้งที่ CI รัน PR ที่ push 15 ครั้งจะมีคอมเมนต์บอต 75 ใบ
วิธีแก้คือซ่อน marker ไว้ในคอมเมนต์ แล้วครั้งต่อไปค้นหา marker นั้นเพื่อ **แก้ของเดิม**

```js
const marker = `<!-- ci-lab-report:${key} -->`;
const existing = comments.find((c) => c.body?.includes(marker));
existing ? await updateComment(...) : await createComment(...);
```

ดูของจริงได้ที่ [`.github/actions/pr-comment/action.yml`](../.github/actions/pr-comment/action.yml)

> **ข้อจำกัดที่ต้องรู้:** PR ที่เปิดจาก fork จะได้ token แบบอ่านอย่างเดียว คอมเมนต์ไม่ได้
> ทางออกคือใช้ `workflow_run` แยกอีกชั้น หรือยอมให้ข้ามไป (repo นี้เลือกข้ามแล้วเตือนไว้
> เพราะผลการตรวจยังอยู่ครบในหน้า Summary)

## เปลี่ยน alert ให้เป็นงานที่มีเจ้าของ

`security-issues.yml` จะดึง alert ที่ยังเปิดค้างบน `main` มาสรุปเป็น **Issue ใบเดียว**
ที่อัปเดตตัวเองทุกวัน และ **ปิดตัวเองอัตโนมัติ** เมื่อไม่เหลือ alert แล้ว

ทำไมใช้ใบเดียว ไม่แยกใบต่อ alert

- alert หนึ่งตัวมักโผล่หลายจุด ถ้าแยกใบจะได้ issue 40 ใบจากปัญหาเดียว
- ปัญหาความปลอดภัยส่วนใหญ่แก้เป็นชุด (อัป base image ทีเดียวหาย 12 รายการ)
- issue ใบเดียวที่อัปเดตเสมอ = ที่เดียวที่ตอบได้ว่า "ตอนนี้เราเหลืออะไรค้างอยู่"

ถ้าทีมอยากได้แบบแยกใบ ให้เพิ่มเงื่อนไขว่าเฉพาะ `critical` เท่านั้นที่แยกใบ

## อะไรควรบล็อกการ merge

นี่คือการตัดสินใจเชิงนโยบาย ไม่ใช่เชิงเทคนิค — และเป็นจุดที่ทีมต้องคุยกันให้จบ

| ด่าน                                    | บล็อก | เหตุผล                                     |
| --------------------------------------- | ----- | ------------------------------------------ |
| ฟอร์แมต / lint / typecheck / test       | ✅    | แก้ง่าย ชัดเจน ไม่มีข้อถกเถียง             |
| Secret scanning                         | ✅    | ค่าลับหลุดคือความเสียหายที่ย้อนกลับไม่ได้  |
| SAST ระดับ error                        | ✅    | ช่องโหว่ที่เครื่องมือมั่นใจสูง             |
| SAST ระดับ warning                      | ❌    | มี false positive พอสมควร ให้รายงานแทน     |
| SCA — production dependency ระดับ high+ | ✅    | ของที่ถูก deploy จริง                      |
| SCA — devDependency                     | ❌    | ไม่ได้ขึ้น production (แต่ยังรายงาน)       |
| Container — ช่องโหว่ที่มีแพตช์แล้ว      | ✅    | แก้ได้ด้วยการอัป base image                |
| Container — ช่องโหว่ที่ยังไม่มีแพตช์    | ❌    | บล็อกไปก็แก้ไม่ได้ กลายเป็นการขวางงานเฉย ๆ |
| Container — รันด้วย root                | ✅    | เป็นตัวคูณความรุนแรงของช่องโหว่ทุกตัว      |

**กฎเหล็ก: ห้ามบล็อกด้วยเกณฑ์ที่ทีมแก้เองไม่ได้** ไม่งั้นจะจบที่การปิดการตรวจทิ้ง

## ตั้งค่าการบล็อกจริง (ทำที่ repo ไม่ใช่ในไฟล์ workflow)

ไฟล์ workflow บอกได้แค่ว่า check นั้น "แดงหรือเขียว"
ส่วนการบังคับว่า **แดงแล้วห้าม merge** ต้องตั้งที่ **Settings → Rules → Rulesets**

รันสคริปต์นี้แทนการคลิกทีละช่อง

```bash
./scripts/setup-repo-protection.sh <owner>/<repo>
```

สิ่งที่สคริปต์ตั้งให้

1. ห้าม push ตรงเข้า `main` — ต้องผ่าน Pull Request และมีคนรีวิวอย่างน้อย 1 คน
2. **required status checks** — job ทั้ง 6 ต้องเขียว
   (ใช้ชื่อ **job** ไม่ใช่ชื่อ workflow — จุดนี้พลาดกันบ่อย)
3. **code scanning merge protection** — ถ้ามี alert ระดับ high ขึ้นไปค้างอยู่ ให้บล็อก
4. ห้ามลบ branch และห้าม force push

> `strict_required_status_checks_policy: true` หมายถึง branch ต้อง rebase/merge main ล่าสุดเข้ามาก่อน
> เพื่อกัน "semantic conflict" — PR สองใบที่ต่างคนต่างเขียว แต่พอรวมกันแล้วพัง

## ของที่ยังต้องกดเปิดเองในหน้าเว็บ

`Settings → Code security` — ตั้งผ่าน API ไม่ได้ทั้งหมด จึงต้องกดเอง

- **Secret scanning** + **Push protection** — บล็อกค่าลับตั้งแต่ตอน push
- **Dependabot alerts** + **Dependabot security updates** — เปิด PR แก้ CVE ให้อัตโนมัติ
- **Private vulnerability reporting** — ช่องทางให้คนนอกแจ้งช่องโหว่แบบไม่เปิดเผยต่อสาธารณะ
