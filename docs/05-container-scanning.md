# 05 — Container Scanning

> workflow: [`.github/workflows/container-scan.yml`](../.github/workflows/container-scan.yml) · คอนฟิก: [`.hadolint.yaml`](../.hadolint.yaml) · สถานะ: **บล็อกการ merge**

## ทำไม SCA อย่างเดียวไม่พอ

`npm audit` เห็นเฉพาะของที่อยู่ใน `package-lock.json`
แต่ image ที่เรา deploy จริงมีมากกว่านั้นเยอะ

```
image ของแอป Node.js หนึ่งตัว
├── โค้ดของเรา                    <- SAST ดูแล
├── node_modules                  <- SCA ดูแล
├── Node.js runtime               <- ไม่มีใครดูแล ถ้าไม่มีด่านนี้
├── openssl, zlib, busybox, ...   <- ไม่มีใครดูแล ถ้าไม่มีด่านนี้
└── ca-certificates, apk, ...     <- ไม่มีใครดูแล ถ้าไม่มีด่านนี้
```

ช่องโหว่ชื่อดังหลายตัว (เช่นฝั่ง openssl หรือ glibc) อยู่ในชั้นที่ `npm audit` มองไม่เห็นเลย

## ด่านนี้ตรวจ 2 เรื่องที่ไม่เหมือนกัน

### 1. วิธีเขียน Dockerfile — Hadolint

ตรวจ "นิสัยการเขียน" ที่ทำให้ image ใหญ่เกินจำเป็น build ช้า หรือไม่ปลอดภัย เช่น

| ปัญหา                              | ทำไมถึงแย่                                      |
| ---------------------------------- | ----------------------------------------------- |
| `FROM node:latest`                 | build วันนี้กับพรุ่งนี้ได้คนละของ สืบย้อนไม่ได้ |
| ไม่มี `USER`                       | container รันด้วย root                          |
| `RUN` ต่อกันหลายบรรทัด             | เพิ่ม layer โดยไม่จำเป็น                        |
| `ADD` จาก URL ภายนอก               | ดึงของที่ตรวจสอบไม่ได้เข้ามาในทุกครั้งที่ build |
| `apt-get install` โดยไม่ล้าง cache | image บวมโดยเปล่าประโยชน์                       |

### 2. ของข้างใน image — Trivy

Trivy จะ "แกะ" image ออกมาดูทีละ layer แล้วเทียบรายการแพ็กเกจกับฐานข้อมูลช่องโหว่
ทั้งแพ็กเกจของ OS (apk/apt/yum) และ dependency ของภาษา (npm, pip, go.mod)
พร้อมกับสแกนหาค่าลับที่เผลอ `COPY` ติดเข้าไปด้วย

## นโยบายที่ใช้: บล็อกเฉพาะตัวที่ "แก้ได้"

```bash
trivy image ... --ignore-unfixed
```

`--ignore-unfixed` คือหัวใจของการทำให้ด่านนี้ใช้งานได้จริง

- ช่องโหว่ที่ **มีเวอร์ชันแก้แล้ว** → บล็อก เพราะแก้ได้ด้วยการอัป base image
- ช่องโหว่ที่ **ยังไม่มีแพตช์จากต้นทาง** → รายงานให้รู้ แต่ไม่บล็อก

ถ้าบล็อกทั้งหมด ทีมจะติดอยู่กับสิ่งที่ตัวเองแก้ไม่ได้ แล้วสุดท้ายจะเลือกปิดการตรวจทิ้ง

## กฎของเราเอง: ห้ามรันด้วย root

นอกจากรายการ CVE แล้ว workflow นี้ยังเช็คตรง ๆ ว่า image ตั้ง `USER` ที่ไม่ใช่ root หรือเปล่า

```bash
docker image inspect "$IMAGE" --format '{{.Config.User}}'
```

เพราะข้อนี้ไม่ใช่ CVE แต่เป็นตัวคูณความรุนแรงของ CVE ทุกตัว —
ช่องโหว่ที่ควรจะทำได้แค่อ่านไฟล์ จะกลายเป็นยึด container ได้ทั้งตัวถ้ารันด้วย root

## วิธีลดช่องโหว่ใน image แบบได้ผลที่สุด

1. **อัป base image ให้ใหม่** — แก้ได้เกินครึ่งด้วยข้อนี้ข้อเดียว และ Dependabot ตามให้ได้
2. **ใช้ image ที่เล็กลง** — `alpine` หรือ `distroless` มีของน้อยกว่า ช่องโหว่ก็น้อยกว่าตามธรรมชาติ
3. **multi-stage build** — ของที่ใช้ตอน build (คอมไพเลอร์, devDependencies) ไม่ควรติดไปกับ image ที่ deploy
4. **pin เวอร์ชันของ base image** — `node:24.21.0-alpine` ไม่ใช่ `node:latest`
   เพื่อให้รู้ว่าวันนี้เรา deploy อะไรอยู่ และอัปเมื่อไหร่
5. **ถอดของที่ไม่ได้ใช้ตอนรันออก**

Dockerfile ใน repo นี้ทำครบทั้งห้าข้อ ใช้เป็นแม่แบบได้

### กรณีจริงจาก repo นี้: ถอด npm ออกจาก image แล้วช่องโหว่หายหมด

ตอนสแกน image ของแล็บนี้ครั้งแรก (base image `node:24.21.0-alpine` ล่าสุด) Trivy รายงาน
ช่องโหว่ระดับ HIGH ที่มีแพตช์แล้ว 4 รายการ — ทั้งหมดมาจาก `brace-expansion`, `ip-address`, `tar`
ซึ่ง **ไม่ใช่ dependency ของแอปเราเลย** แต่เป็นไลบรารีที่ติดมากับตัว `npm` ใน base image

แต่ตอนรันจริงเราเรียกแค่ `node dist/index.js` ไม่ได้ใช้ npm สักนิด จึงถอดทิ้งได้

```dockerfile
RUN apk --no-cache upgrade \
  && rm -rf /usr/local/lib/node_modules/npm /usr/local/bin/npm /usr/local/bin/npx
```

ผลคือช่องโหว่เหลือ **ศูนย์รายการทุกระดับ** โดยที่แอปยังทำงานเหมือนเดิม

บทเรียนคือ **ของที่ไม่ได้ใช้ตอนรัน = พื้นที่โจมตีที่ได้มาฟรี ๆ โดยไม่ได้ประโยชน์อะไรตอบแทน**
คำถามที่ควรถามกับทุกอย่างใน image คือ "ถ้าลบออก แอปยังทำงานได้ไหม" ถ้าตอบว่าได้ ก็ควรลบ

## ปรับจูนเครื่องมืออย่างมีเหตุผล

ใน [`.hadolint.yaml`](../.hadolint.yaml) เราตั้ง

```yaml
failure-threshold: warning # info/style ยังแสดงผล แต่ไม่ทำให้ CI แดง
ignored:
  - DL3066 # พร้อมคอมเมนต์อธิบายว่าทำไมถึงยกเว้น
```

การยกเว้นไม่ใช่เรื่องผิด แต่**ต้องอธิบายได้ว่าทำไม** และต้องยกเว้นให้แคบที่สุดเท่าที่จำเป็น

## บทเรียน: รายงานต้องบอก "อะไรพัง" ให้ตรง

รอบหนึ่งด่านนี้ขึ้นแดงพร้อมข้อความว่า **"image รันด้วย root"** ทั้งที่ `Dockerfile` มี `USER node` อยู่ชัด ๆ

ความจริงคือ `docker build` ล้มก่อนตั้งแต่ต้น เพราะ `apk` ดึง index ของ Alpine ไม่ได้

```
WARNING: fetching https://dl-cdn.alpinelinux.org/alpine/v3.24/main/x86_64/APKINDEX.tar.gz: TLS: unspecified error
ERROR: Not continuing due to stale/unavailable repositories.
```

พอ build ล้ม step ที่ตรวจ `USER` ก็ถูกข้าม (`outcome = skipped`) แล้วโค้ดสรุปผลของเราเช็คแค่ว่า
"ไม่ใช่ success" จึงเหมาเอาว่าเป็น root

ผลคือคนอ่านรายงานจะไปไล่แก้ `Dockerfile` ที่ไม่ได้ผิดอะไรเลย — **รายงานที่ผิดแย่กว่าไม่มีรายงาน**
เพราะมันพาคนไปผิดทางและกัดกร่อนความเชื่อถือในระบบทั้งระบบ

สองสิ่งที่แก้

1. แยกกรณี `build ไม่สำเร็จ` ออกมารายงานต่างหาก ก่อนจะไปสรุปผลการตรวจใด ๆ
2. ให้ `docker build` ลองใหม่ได้ถึง 3 ครั้ง เพราะขั้นตอนนี้ต้องดึงของจากอินเทอร์เน็ตตลอด
   (base image, apk index, npm registry) — **ความล้มเหลวของเครือข่ายไม่ใช่ความล้มเหลวของคุณภาพโค้ด**

หลักเดียวกับเรื่อง artifact ใน `docs/06-alerts-and-gates.md`: ทุกครั้งที่ CI แดง
ต้องตอบได้ว่าแดงเพราะโค้ดหรือแดงเพราะโครงสร้างพื้นฐาน และสองอย่างนี้ต้องดูออกจากรายงานทันที

## ขั้นต่อไปในงานจริง

- **SBOM** — ออกรายการส่วนประกอบของ image (`trivy image --format cyclonedx`)
  เก็บไว้เพื่อให้ตอบได้ทันทีว่า "เรามีแพ็กเกจที่เพิ่งประกาศช่องโหว่ตัวนี้อยู่ใน production ไหม"
- **ลงลายเซ็น image** ด้วย cosign แล้วให้ cluster ยอมรับเฉพาะ image ที่ลงลายเซ็นแล้ว
- **สแกน image ที่อยู่บน production ซ้ำตามเวลา** ไม่ใช่สแกนแค่ตอน build
  เพราะ image ที่ deploy ไปเมื่อสามเดือนก่อนไม่ได้ปลอดภัยขึ้นตามเวลา
