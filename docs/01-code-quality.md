# 01 — Code Quality & Formatting

> workflow: [`.github/workflows/quality.yml`](../.github/workflows/quality.yml) · สถานะ: **บล็อกการ merge**

## ด่านนี้ตรวจอะไร

| การตรวจ                       | เครื่องมือ                   | ทำไมต้องมี                                                                   |
| ----------------------------- | ---------------------------- | ---------------------------------------------------------------------------- |
| ฟอร์แมตโค้ด                   | Prettier                     | ให้ diff ใน PR มีแต่การเปลี่ยนที่มีความหมายจริง ไม่ใช่การขยับวรรค/ย้ายวงเล็บ |
| รูปแบบการเขียนและบั๊กระดับต้น | ESLint (+ typescript-eslint) | จับ unused variable, `==` ที่ควรเป็น `===`, `any` ที่หลุดเข้ามา, `eval`      |
| ชนิดข้อมูล                    | `tsc --noEmit`               | บั๊กจำนวนมากใน JavaScript คือบั๊กเรื่องชนิดข้อมูล ตัวนี้จับได้ก่อนรันจริง    |
| พฤติกรรมของโปรแกรม            | Vitest                       | เทสคือเกณฑ์ว่าโค้ดยัง "ทำงานถูก" หลังแก้                                     |

## ทำไมฟอร์แมตถึงสำคัญพอที่จะบล็อกการ merge

เพราะมันไม่ใช่เรื่องความสวยงาม แต่เป็นเรื่องของ **ต้นทุนการรีวิว**
ถ้าแต่ละคนตั้งค่า editor ต่างกัน PR หนึ่งใบจะมี diff ปนกันระหว่าง "โค้ดที่เปลี่ยนจริง" กับ "วรรคที่ขยับ"
คนรีวิวจะมองไม่ออกว่าอะไรคืออะไร และจะเริ่มกด Approve แบบผ่าน ๆ

วิธีที่ถูกคือ **ห้ามเถียงเรื่องสไตล์ ให้เครื่องมือตัดสิน** แล้วบังคับใน CI ทีเดียว

## เทคนิคที่ใช้ในไฟล์นี้: รันให้ครบก่อนค่อยตัดสิน

ปกติถ้าเขียน step เรียงกันเฉย ๆ พอ Prettier ล้ม workflow จะหยุดทันที
คนเขียนโค้ดก็จะแก้ฟอร์แมต push ใหม่ แล้วเพิ่งมารู้ว่า ESLint ก็ไม่ผ่าน — เสียเวลาไปอีกหนึ่งรอบ

ใน `quality.yml` ทุก step ตรวจจึงตั้ง `continue-on-error: true` แล้วเก็บผลไว้ที่ `steps.<id>.outcome`
พอครบแล้วค่อยมี step สุดท้ายที่เขียนตารางสรุปและ `exit 1` ถ้ามีข้อไหนไม่ผ่าน

```yaml
- name: ตรวจฟอร์แมตด้วย Prettier
  id: format
  continue-on-error: true
  run: npm run format:check
```

## SARIF คืออะไร ทำไม ESLint ต้องออกไฟล์นี้

SARIF (Static Analysis Results Interchange Format) คือ **รูปแบบมาตรฐานกลางของ "ผลการตรวจโค้ด"**
เครื่องมือคนละยี่ห้อ (ESLint, Semgrep, Trivy, Gitleaks, CodeQL) ออกผลเป็น SARIF ได้เหมือนกันหมด
GitHub จึงรับไฟล์เดียวแล้วเอาไปแสดงเป็น alert ปักหมุดถึงบรรทัดโค้ดได้ ไม่ต้องรู้จักเครื่องมือเป็นราย ๆ

```yaml
- uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: eslint.sarif
    category: eslint # ต้องแยก category ไม่งั้นผลของเครื่องมือหนึ่งจะไปทับอีกเครื่องมือ
```

> การอัปโหลด SARIF ต้องมีสิทธิ์ `security-events: write` และใช้ได้ฟรีกับ **public repository**
> ถ้าเป็น private repo ต้องมี GitHub Advanced Security

## ให้ทีมไม่ต้องเจอ CI แดงบ่อย ๆ

ตั้ง hook ฝั่งเครื่องตัวเองเพิ่ม เพื่อให้แก้ตั้งแต่ก่อน push (แนวคิด shift left)

```bash
npm run format && npm run lint && npm run typecheck && npm test
```

หรือใช้ `lint-staged` + `husky` ให้รันอัตโนมัติตอน commit เฉพาะไฟล์ที่แก้

## ข้อยกเว้นควรอยู่ใน config ไม่ใช่ในโค้ด

`src/index.ts` จำเป็นต้องพิมพ์ข้อความตอนเซิร์ฟเวอร์เริ่มทำงาน ซึ่งชน `no-console`
ตอนแรกเราใช้วิธีที่คุ้นเคยกันดี

```ts
// eslint-disable-next-line no-console
console.log(`task service ฟังอยู่ที่พอร์ต ${config.port}`);
```

แต่พอผล ESLint ถูกอัปโหลดเป็น SARIF ขึ้นแท็บ Security กลับมี alert `no-console` ค้างอยู่หนึ่งรายการ
เพราะตัวแปลง SARIF รายงาน "จุดที่ถูก disable" ออกมาด้วย — กลายเป็นของค้างในแท็บ Security
ที่ไม่มีใครกล้าปิดเพราะไม่รู้ที่มา

ทางที่สะอาดกว่าคือทำเป็น**ข้อยกเว้นเชิงนโยบาย**ใน `eslint.config.js`

```js
{
  // จุดเริ่มโปรแกรมเป็นที่เดียวที่อนุญาตให้พิมพ์ออกหน้าจอได้
  files: ['src/index.ts'],
  rules: { 'no-console': 'off' },
}
```

ต่างกันตรงที่อย่างแรกคือ "คนคนหนึ่งขอข้าม" ส่วนอย่างหลังคือ "ทีมตกลงกันว่าที่นี่ยกเว้นได้"
และอ่านรวมทีเดียวได้ว่ามีข้อยกเว้นอะไรอยู่บ้าง

## ข้อควรระวัง

- **อย่าเปิดกฎทุกข้อในวันแรก** ถ้า repo เก่ามีปัญหา 3,000 จุด ให้เริ่มจากตั้งกฎเป็น `warn`
  แล้วค่อยไล่ยกระดับเป็น `error` ทีละกลุ่ม ไม่งั้นทีมจะเลือกวิธีปิด CI แทนการแก้
- **แยกกฎของ Prettier ออกจาก ESLint** ใน `eslint.config.js` จึงมี `eslint-config-prettier` ต่อท้ายสุด
  เพื่อปิดกฎ ESLint ที่ทับซ้อนกับงานฟอร์แมต ไม่งั้นสองตัวจะสั่งกลับทางกันจนแก้ไม่จบ
