# 03 — SAST (Static Application Security Testing)

> workflow: [`.github/workflows/sast.yml`](../.github/workflows/sast.yml) · กฎที่เขียนเอง: [`.semgrep/rules/`](../.semgrep/rules/) · สถานะ: **error = บล็อก / warning = รายงาน**

## SAST คืออะไร

การ **อ่านโค้ดที่เราเขียนเอง เพื่อหาช่องโหว่ โดยไม่ต้องรันโปรแกรม**

ตัวอย่างสิ่งที่จับได้

- SQL injection — เอาค่าจากผู้ใช้ไปต่อสตริงเป็น query
- Command injection — เอาค่าจากผู้ใช้ไปแทรกในคำสั่ง shell
- Path traversal — เอาค่าจากผู้ใช้ไปต่อเป็น path ของไฟล์
- การเข้ารหัสที่อ่อน — MD5/SHA1 กับรหัสผ่าน, `Math.random()` กับโทเคน
- การปิดการตรวจ certificate หรือปิดการ verify ลายเซ็น JWT

## SAST ต่างจาก Linter อย่างไร

|                                           | ESLint                    | Semgrep / CodeQL                                                |
| ----------------------------------------- | ------------------------- | --------------------------------------------------------------- |
| มองอะไร                                   | รูปแบบการเขียนในไฟล์เดียว | โครงสร้างโค้ด + **เส้นทางของข้อมูล (dataflow)**                 |
| ตอบได้ไหมว่า "ค่านี้มาจากผู้ใช้หรือเปล่า" | ไม่ได้                    | ได้ (taint analysis)                                            |
| ตัวอย่างคำถามที่ตอบได้                    | "ตัวแปรนี้ไม่ได้ใช้"      | "`req.query.file` เดินทางไปถึง `fs.readFile` โดยไม่ผ่านการตรวจ" |

นี่คือเหตุผลที่มีทั้งสองอย่างใน pipeline — ไม่ได้ทำงานซ้ำกัน

## ชุดกฎที่ repo นี้ใช้

```bash
semgrep scan \
  --config .semgrep/rules \   # กฎของทีมเราเอง
  --config p/typescript \     # กฎสำเร็จรูปของ TypeScript
  --config p/nodejs \         # กฎเฉพาะ Node.js
  --config p/owasp-top-ten    # กฎที่อิง OWASP Top 10
```

จงใจ**ไม่ใช้** `--config auto` เพราะอยากให้อ่านออกได้ว่าใช้กฎชุดไหนบ้าง
และผลการตรวจของวันนี้กับเดือนหน้าต้องอธิบายได้ว่าทำไมต่างกัน

## เขียนกฎเองได้ และควรเขียน

กฎสำเร็จรูปรู้จักช่องโหว่ทั่วไป แต่ไม่รู้จัก "กติกาของบ้านเรา"
เช่น ทีมตกลงกันว่าห้ามเรียก `exec` ด้วยสตริงที่ประกอบจากตัวแปร — เขียนเป็นกฎได้แบบนี้

```yaml
- id: gbtech-exec-with-interpolation
  languages: [javascript, typescript]
  severity: ERROR
  message: ห้ามประกอบคำสั่ง shell ด้วยการแทรกตัวแปร ให้ใช้ execFile/spawn แทน
  patterns:
    - pattern-either:
        - pattern: $CP.exec(`...${$X}...`, ...)
        - pattern: $CP.execSync(`...${$X}...`, ...)
```

pattern ของ Semgrep เขียนเหมือนโค้ดจริง ไม่ใช่ regex — `$X` คือตัวแปรอะไรก็ได้ และ `...` คือ "อะไรก็ได้ตรงนี้"
ทำให้คนในทีมที่ไม่ใช่สาย security ก็เขียนกฎเพิ่มได้

> ข้อควรระวังเรื่อง YAML: ถ้า pattern มี `:` อยู่ข้างใน (เช่น `{ error: $ERR.stack }`)
> ต้องครอบด้วยเครื่องหมายคำพูด ไม่งั้น YAML จะตีความเป็น mapping แล้วไฟล์กฎจะพังทั้งไฟล์

## นโยบาย: อะไรบล็อก อะไรแค่เตือน

| ระดับใน SARIF | ระดับ Semgrep | นโยบายของ repo นี้              |
| ------------- | ------------- | ------------------------------- |
| `error`       | ERROR         | **บล็อกการ merge**              |
| `warning`     | WARNING       | รายงานใน Summary + Security tab |
| `note`        | INFO          | รายงานอย่างเดียว                |

เหตุผลที่ไม่บล็อกทุกระดับ: ถ้า CI แดงตลอดเวลา ทีมจะเรียนรู้ที่จะเพิกเฉย
และวันที่เจอของจริงระดับ critical ก็จะไม่มีใครสนใจ

## จัดการ false positive

SAST มี false positive แน่นอน โดยเฉพาะกฎที่เดาเจตนาจากชื่อตัวแปร
เมื่อมั่นใจว่าไม่ใช่ช่องโหว่จริง ให้เขียนกำกับบรรทัดนั้น

```ts
// nosemgrep: gbtech-hardcoded-credential-in-source -- ค่านี้เป็น placeholder ในเทส (อนุมัติโดยทีม security)
const apiKey = 'dummy-value-for-test';
```

**ต้องเขียนเหตุผลเสมอ** การยกเว้นที่ไม่มีเหตุผลกำกับ คือหนี้ที่ไม่มีใครกล้าจ่ายคืน

## ข้อจำกัดของ SAST

- ไม่รู้บริบทการใช้งานจริง เช่น endpoint นี้อยู่หลัง VPN หรือเปิดสาธารณะ
- จับ **logic flaw** ไม่ได้ เช่น ลืมตรวจว่าผู้ใช้เป็นเจ้าของข้อมูลนั้นจริงไหม
- โค้ดที่ประกอบขึ้นตอน runtime (reflection, `eval` ของสตริงจากฐานข้อมูล) มองไม่เห็น

SAST จึงเป็นด่านหนึ่งของหลายด่าน ไม่ใช่คำตอบสุดท้ายของความปลอดภัย

## CodeQL — SAST อีกตัวที่ GitHub ให้มาเอง

> workflow: [`.github/workflows/codeql.yml`](../.github/workflows/codeql.yml)

CodeQL ทำงานคนละแบบกับ Semgrep: มันแปลงโค้ดทั้งโปรเจกต์เป็น **ฐานข้อมูล**
แล้วใช้ภาษา query (คล้าย SQL) ไล่ถามว่า "มีเส้นทางไหนที่ข้อมูลจากแหล่งที่ไม่น่าเชื่อถือ
เดินไปถึงจุดที่อันตรายได้บ้าง" จึงตามข้ามไฟล์ข้ามฟังก์ชันได้ลึกกว่า

|                        | Semgrep                  | CodeQL                   |
| ---------------------- | ------------------------ | ------------------------ |
| ความเร็ว               | เร็วมาก (วินาที–นาที)    | ช้ากว่า (นาที–สิบนาที)   |
| เขียนกฎเองยากง่าย      | ง่าย เขียนเหมือนโค้ดจริง | ต้องเรียนภาษา QL         |
| ความลึกของการวิเคราะห์ | ดี                       | ลึกกว่า โดยเฉพาะข้ามไฟล์ |
| ผลขึ้นแท็บ Security    | ต้องอัปโหลด SARIF เอง    | ขึ้นให้เอง               |
| ค่าใช้จ่าย             | ฟรี (เวอร์ชัน OSS)       | ฟรีสำหรับ public repo    |

**ใช้ทั้งคู่ไม่ใช่เรื่องฟุ่มเฟือย** — Semgrep ไว้บังคับกติกาของทีมแบบเร็ว ๆ ในทุก PR
ส่วน CodeQL ไว้หาช่องโหว่เชิงลึกที่กฎง่าย ๆ มองไม่เห็น

### ข้อสังเกตสำหรับภาษาที่ต้องคอมไพล์

JavaScript/TypeScript ไม่ต้อง build ก่อน แต่ Java, C#, Go, C/C++ ต้องมี
`github/codeql-action/autobuild` หรือเขียนคำสั่ง build เอง เพราะ CodeQL ต้องดู
สิ่งที่คอมไพเลอร์เห็นจริง ๆ

### รันซ้ำตามตารางเวลา ทั้งที่โค้ดไม่เปลี่ยน

`schedule:` ใน workflow ไม่ใช่ของเกิน — เพราะ **กฎใหม่ถูกเพิ่มเข้ามาเรื่อย ๆ**
โค้ดที่ผ่านเมื่อเดือนที่แล้ว อาจไม่ผ่านกฎที่เพิ่งออกเมื่อวาน

## บทเรียนจากการรันจริง: ด่านที่ไม่เคยแดง อาจเป็นด่านที่เสีย

ตอนสาธิต PR ที่จงใจใส่ช่องโหว่ 5 แบบ ด่าน SAST กลับรายงานว่า **"ไม่พบช่องโหว่ ✅"**
ทั้งที่รัน Semgrep ตัวเดียวกันในเครื่องแล้วเจอ 8 รายการ

สาเหตุอยู่ที่วิธีอ่านไฟล์ SARIF ไม่ใช่ที่ตัวสแกน

```bash
# โค้ดเดิม — ได้ 0 เสมอ
jq '[.runs[].results[] | select(.level == "error")] | length' semgrep.sarif
```

SARIF ของ Semgrep **ไม่ได้ใส่ `level` ไว้ในผลแต่ละรายการ** แต่ไปประกาศไว้ที่นิยามของกฎ
(`runs[].tool.driver.rules[].defaultConfiguration.level`) ตามสเปกที่อนุญาตให้ละไว้ได้
ถ้าค่าเท่ากับค่าปริยายของกฎนั้น

ทางแก้คือไล่ย้อนจาก `ruleId` ของผลไปหานิยามของกฎก่อน แล้วค่อยนับ

```bash
jq '[ .runs[] as $run
  | (($run.tool.driver.rules // []) + (($run.tool.extensions // []) | map(.rules // []) | add // [])) as $rules
  | $run.results[] | . as $res
  | { level: ( $res.level
               // ([$rules[] | select(.id == $res.ruleId) | .defaultConfiguration.level] | first)
               // "warning" ), ... } ]' semgrep.sarif
```

> **สิ่งที่ควรติดตัวไป: ทุกครั้งที่ตั้งด่านใหม่ ต้องทดสอบด้วยโค้ดที่ผิดจริง ๆ ว่ามันแดงได้**
> ไม่ใช่เห็นว่าเขียวแล้วสบายใจ — pipeline ที่เขียวเพราะเสียนั้นอันตรายกว่าไม่มี pipeline
> เพราะมันให้ความมั่นใจปลอม ๆ

การมี PR ตัวอย่างที่จงใจทำผิด (อย่างใน repo นี้) จึงไม่ใช่แค่สื่อการสอน
แต่เป็น **การทดสอบตัว pipeline เอง** ที่ควรรันซ้ำทุกครั้งที่แก้ไฟล์ workflow

## บทเรียนที่สอง: เครื่องมือจับช่องโหว่ในตัว pipeline เราเอง

พอแก้เรื่องการนับแล้วรันใหม่ Semgrep รายงาน error ในไฟล์ของ pipeline เอง

```
.github/actions/pr-comment/action.yml:31  github-script-injection
```

เพราะเราเขียน `const key = ${{ toJSON(inputs.key) }};` ซึ่งเป็นการ **แทรกค่าลงไปในโค้ด**
รูปแบบเดียวกับ SQL injection ถ้าค่าที่แทรกมาจากสิ่งที่ผู้อื่นควบคุมได้ (เช่นชื่อ branch หรือหัวข้อ PR)
ก็รันโค้ดอะไรก็ได้ในบริบทที่มี `GITHUB_TOKEN` อยู่ในมือ

ทางแก้มาตรฐานคือส่งผ่าน `env:` แล้วอ่านจาก `process.env`

```yaml
env:
  REPORT_KEY: ${{ inputs.key }}
with:
  script: |
    const key = process.env.REPORT_KEY; # ค่าอยู่ในตัวแปร ไม่ใช่ในโค้ด
```

**ไฟล์ CI/CD เป็นโค้ดที่ต้องถูกตรวจเหมือนโค้ดอื่น** — มันรันด้วยสิทธิ์สูงและเข้าถึง secret ได้

## warning ที่ยอมรับไว้โดยตั้งใจ

Semgrep รายงาน `github-actions-mutable-action-tag` ราว 24 จุด เพราะ repo นี้อ้าง action
ด้วย tag (`actions/checkout@v7`) ไม่ใช่ commit SHA

คำแนะนำนั้นถูกต้องสำหรับ production — tag ถูกย้ายได้ ถ้าบัญชีผู้พัฒนา action ถูกยึด
โค้ดที่รันใน pipeline เราก็เปลี่ยนโดยที่ไฟล์ของเราไม่ได้แก้อะไรเลย

```yaml
# แบบที่ปลอดภัยกว่า (Dependabot อัป SHA ให้ได้เหมือนกัน)
uses: actions/checkout@08c6903cd8c0fde910a37f88322edcfb5dd907a8 # v7.0.1
```

repo นี้เลือกใช้ tag เพราะเป็นสื่อการสอนที่คนต้องอ่านแล้วเข้าใจทันที
และ**บันทึกเหตุผลไว้ตรงนี้** — นั่นคือวิธีจัดการ warning ที่ถูกต้อง: ตัดสินใจอย่างมีเหตุผลและเขียนไว้
ไม่ใช่ปิดกฎทิ้งเงียบ ๆ หรือปล่อยค้างโดยไม่มีใครรู้ว่าทำไม
