# 04 — SCA (Software Composition Analysis)

> workflow: [`.github/workflows/sca.yml`](../.github/workflows/sca.yml) · [`.github/dependabot.yml`](../.github/dependabot.yml) · สถานะ: **production dependency ระดับ high ขึ้นไป = บล็อก**

## ทำไมด่านนี้สำคัญกว่าที่คิด

ในโปรเจกต์ Node.js ทั่วไป โค้ดที่ทีมเขียนเองมักไม่ถึง 5% ของโค้ดทั้งหมดที่ถูกรันจริง
ที่เหลือคือ dependency และ dependency ของ dependency ลงไปอีกหลายชั้น

แปลว่า **ต่อให้โค้ดเราไม่มีช่องโหว่เลย แอปก็ยังมีช่องโหว่ได้** จากของที่เราแค่ `npm install` เข้ามา
และเรามักไม่รู้ด้วยซ้ำว่ามีแพ็กเกจพวกนั้นอยู่

```bash
npm ls --all | wc -l   # ลองรันดูในโปรเจกต์ของตัวเอง แล้วจะเข้าใจ
```

## เครื่องมือ 3 ตัวที่ใช้ร่วมกัน

| เครื่องมือ         | บทบาท        | จุดเด่น                                                      |
| ------------------ | ------------ | ------------------------------------------------------------ |
| `npm audit`        | ตรวจตอน CI   | แยก production / dev ได้ และบอกวิธีแก้                       |
| Trivy (`trivy fs`) | ตรวจตอน CI   | อ่าน lock file เห็นทุกชั้น และออก SARIF ขึ้นแท็บ Security    |
| Dependabot         | เฝ้าตลอดเวลา | **เปิด PR พร้อมเวอร์ชันใหม่มาให้เลย** ไม่ใช่แค่บอกว่ามีปัญหา |

Dependabot คือตัวที่เปลี่ยนพฤติกรรมทีมได้จริง เพราะลดงานจาก "ต้องไปไล่หาว่าอัปยังไง"
เหลือแค่ "รีวิว PR แล้วกด merge"

## นโยบายที่ใช้: แยก production ออกจาก dev

```yaml
# บล็อก: เฉพาะของที่ถูก deploy จริง
npm audit --omit=dev --audit-level=high

# รายงาน: ทั้งหมด รวม devDependency
npm audit --json
```

เหตุผล: ช่องโหว่ใน `vitest` หรือ `eslint` ไม่ได้ถูกส่งขึ้น production
ความเสี่ยงคนละระดับกับไลบรารีที่รันรับ request จากอินเทอร์เน็ตจริง

ถ้าใช้เกณฑ์เดียวกันหมด ทีมจะเจอ CI แดงจากเรื่องที่ไม่กระทบ production บ่อยจนเลิกเชื่อ pipeline

> แต่ **ไม่ได้แปลว่า devDependency ไม่สำคัญ** — แพ็กเกจฝั่ง dev รันบนเครื่อง dev และบน CI runner
> ซึ่งมักมีสิทธิ์เข้าถึง secret ของโปรเจกต์ การโจมตีแบบ supply chain หลายครั้งเข้ามาทางนี้
> เราจึงยังรายงานให้เห็นเสมอ แค่ไม่บล็อกเท่านั้น

## เรื่องจริงที่เกิดขึ้นกับ repo นี้: เปิด Dependabot ปุ๊บ มี PR 9 ใบทันที

ภายในไม่กี่นาทีหลัง push ครั้งแรก Dependabot เปิด PR มา 9 ใบรวด ทั้งอัป `eslint`,
`@types/node`, เวอร์ชันของ GitHub Actions ที่ใช้ใน workflow และ base image ของ Docker

นี่คือด่านแรกที่ทีมส่วนใหญ่แพ้ — PR ท่วมจนเลิกอ่าน แล้วสุดท้ายก็ปิด Dependabot ทิ้ง
วิธีรับมือที่ได้ผลคือ

1. **จัดกลุ่ม** (`groups:`) ให้การอัปเล็ก ๆ มารวมใน PR เดียว
2. **จำกัดจำนวน PR ที่เปิดพร้อมกัน** (`open-pull-requests-limit`)
3. **เขียนกติกาว่าอะไรไม่รับ** แทนการไล่ปิด PR เงียบ ๆ ทุกสัปดาห์

ตัวอย่างข้อ 3 ที่ repo นี้ใช้จริง — Dependabot เสนออัป base image จาก Node 24 ไป 26
แต่เราตั้งใจอยู่บนสาย LTS จึงเขียนไว้ในคอนฟิกให้ชัด

```yaml
ignore:
  - dependency-name: node
    update-types:
      - version-update:semver-major
```

ส่วนข้อเสนอที่ดีจริงก็ควรรับ — เช่นรอบนี้ Dependabot ชี้ว่า action ที่ pipeline ใช้อยู่
(`actions/checkout@v4`, `actions/github-script@v7`) ตกรุ่นไปหลายเวอร์ชันแล้ว
ซึ่งเป็นสิ่งที่คนมักลืม ทั้งที่ action คือโค้ดของคนอื่นที่รันด้วยสิทธิ์ของ repo เรา

## เมื่อยังไม่มีแพตช์ให้อัป

ลำดับทางเลือก

1. **อัปเวอร์ชันตรง ๆ** — `npm audit fix` หรือแก้ใน `package.json`
2. **บังคับเวอร์ชันของ dependency ชั้นลึก** ด้วย `overrides`

   ```json
   {
     "overrides": {
       "แพ็กเกจที่มีช่องโหว่": "1.2.3"
     }
   }
   ```

3. **ประเมินว่าโดนจริงไหม** — CVE บางตัวอยู่ในฟังก์ชันที่เราไม่เคยเรียกใช้
   (แนวคิด reachability) ถ้าไม่กระทบ ให้บันทึกการยอมรับความเสี่ยงไว้ **พร้อมวันที่ทบทวนอีกครั้ง**
4. **เปลี่ยนไปใช้แพ็กเกจอื่น** ถ้าเจ้าของแพ็กเกจเลิกดูแลแล้ว

ข้อที่ต้องไม่ทำคือปิดการตรวจทิ้งแล้วลืมมันไป

## ทำไมต้องตั้ง schedule ให้รันทุกวัน

เพราะ **CVE ใหม่ถูกประกาศทุกวัน ทั้งที่โค้ดเราไม่ได้เปลี่ยนเลยสักบรรทัด**
แพ็กเกจที่วันนี้สะอาด พรุ่งนี้อาจมี advisory ใหม่ออกมา

```yaml
schedule:
  - cron: '0 2 * * *'
```

ผลของการสแกนตามเวลาจะกลายเป็น Issue อัตโนมัติ (ดู `docs/06-alerts-and-gates.md`)
เพื่อให้มีคนรับผิดชอบ ไม่ใช่แค่ขึ้นแดงอยู่ในหน้า Actions ที่ไม่มีใครเปิด

## นอกเหนือจากช่องโหว่: เรื่องสัญญาอนุญาต (license)

SCA ยังใช้ตรวจ license ของ dependency ได้ด้วย ซึ่งสำคัญมากกับงานที่ส่งให้ลูกค้า
เช่น การเผลอดึงแพ็กเกจ GPL เข้ามาในผลิตภัณฑ์ปิดซอร์ส

```bash
trivy fs . --scanners license --severity HIGH,CRITICAL
```

repo นี้ไม่ได้เปิดไว้เพื่อให้โฟกัสอยู่ที่เรื่องช่องโหว่ก่อน แต่ในงานจริงควรพิจารณา
